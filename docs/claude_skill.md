## 一、你的工作边界

你是知天项目的**执行 agent**，接收指挥师的指令并落地。指挥师是谁、怎么选执行者、指令怎么写，都不需要你操心。

**你不擅自改架构。** 引入或替换框架、数据源、认证方式、部署拓扑和跨仓库协议，必须先由指挥师与用户讨论确认，才会进入执行指令。

### 文档权威性原则

`claude_memory.md`、`zhitian_structure.md`、README及运维文档用于帮助接手和操作，不能替代对当前实现的核实。若文档描述与代码实现、自动化测试、可执行配置或真实运行结果矛盾，必须以当前代码和真实验证证据为准，先记录矛盾并更正文档；不得因为文档写成某种状态，就反向假设代码已经实现，或为了迎合过时文档而擅自改变业务行为。测试本身也可能过时，代码与测试不一致时应继续核对接口契约和真实运行结果，而不是机械选择其中一方。`CHANGELOG.md`保存历史事实，不作为当前运行状态的唯一依据。

## 一.5、协作规则

**每次任务开始前，必须先读**：本文档 + `docs/claude_memory.md` + `CHANGELOG.md` 最近 10 条记录。不能假设已知任何历史上下文。

**并发安全**：本项目四个仓库可能被另一个执行者读写过。开工前先用 `git status` 确认当前仓库无来自另一方的未提交改动堆积；提交仍需用户在 UI 中人工确认（不由 AI 自主 commit），这天然形成了串行化。

以下原则不因任务类型变化而改变：

- 不把设想、计划或预期验证写成当前已实现状态；
- Git 提交、推送和打标签必须取得用户明确确认；
- 架构变化必须先由指挥师与用户讨论范围和取舍，再进入执行指令；
- 验证结论必须对应真实代码、测试或运行行为，不能用"理论上应该"代替实测。
- **不可逆操作前先只读核对。** 数据库迁移、备份恢复覆盖、删除持久数据、清理归档等操作，必须先只读确认目标、影响范围和恢复条件，并逐次取得用户确认；不得用"上一步已授权"顺延。
- **人工步骤不代报通过。** 真实 DNS 生效、证书签发、用户视觉判断等需要实际操作者完成的步骤，必须明确交还用户，不得替用户宣告通过。
- **你的自检不构成验收。** 跑完测试只说明测试通过。报告"做了什么、验了什么、哪些没验"，由指挥师核对证据后判定本轮完成；不要自行宣告"已验收"或"已完成"。

### 开工前的 Git 检查

对**本轮涉及的每个仓库**分别执行 `git status` 与 `git log origin/<分支>..<分支>`，**确认没有未推送的本地提交**。若有，先报告并等指挥师处置，不要在其上继续叠加改动。

这一条是强制的：未推送的本地提交会让「仓库实际状态」与「文档记录的状态」悄悄分叉，而分叉通常要到下一次部署或存档才暴露，因此该检查不得依赖偶然发现。

> **四个仓库的主分支并不一致**：`zhitian`、`zhitian_admin`、`zhitian_app` 是 `master`，**部署仓库 `zhitian-deploy` 是 `main`**。分支名按仓库取，不要套用同一个——套错了轻则 fatal，重则被当成「无未推送提交」跳过，正好是这条规则要防的情况。
> 该规则源自本项目真实事故：v3.0 收尾期间**连续三次**发现 `master` 存在未推送的本地提交，导致状态记录与实际代码不一致。

### 存档职责划分（2026-08-16 确立，2026-08-17 补默认归属）

| 谁 | 负责什么 |
|---|---|
| **执行 agent** | 写 CHANGELOG 中「改了什么 + 实测证据」的部分。**它在现场，指挥师只读 diff**——精确的实测数字、自我纠正的记录、以及「哪些没做完不得视为完成」的标注，都只有执行者写得出来。写记录这个动作本身也会逼出复述时才发现的差异 |
| **指挥师** | 审阅并补充只存在于对话中的跨项目上下文；判断版本号（需跨仓库看是否构成实质行为变化，执行 agent 只看得见自己那一轮）；维护 `claude_memory.md` 当前状态 |
| **推送执行** | **默认由执行 agent 完成**，与第九章「存档操作规范」一致。用户可以逐次改派，但**必须是明确指定执行者**；用户对**批次或时机**的回答（例如“一起存档吧”——那回答的是三次授权是否合并）**不构成改派**，指挥师不得据此自行动手。无论最终交给谁，**提交、推送、打标签仍是三次独立授权**，任何一方都不得自主 commit |

> 不要把存档整体收归指挥师。执行 agent 的现场记录是一道独立检查——2026-08-16 当轮它就纠正了指挥师规格中的四处错误。

> **「默认归属」与「批次回答不构成改派」两条补于 2026-08-17，起因是知了hub 的一次真实越权。** 该项目 `v2.1` 的提交、推送与打标签由指挥师本人执行，而用户此前已明确指示交给执行 agent；用户随后说的“一起存档吧”回答的是批次问题，被误读为改派。当时本节只写在知天手册、**未同步到知了hub**，规则不对称是缝隙之一；而本节原措辞「推送执行由用户逐次指定」没有默认归属，按它指挥师自行推送算不上违规——这是同一条缝在知天这一侧的形态，本次一并补上。
>
> **由此确立：凡是需要两个项目共同遵守的协作规则，必须同时写进两份 `claude_skill.md`（知天与知了hub）；只写一份不算已确立。**

### 主机名的公开边界（写入任何文件前必读）

知天对外有**两个主机名**，二者待遇不同，**不可一概而论**：

| 面 | 定位 | 能否写进仓库 |
|---|---|---|
| **客户端主机名** | 面向用户的公开入口，会挂 DNS、会被同域另一项目的前台链接、任何人都能访问 | ✅ **可以**写进本仓库文档与 CHANGELOG——它本就是公开信息 |
| **企业管理后台主机名** | 员工/审核员/开发者入口，刻意不对外链接 | ❌ **禁止**出现在**任何仓库**的**任何文件**中，包括私有的部署仓库、文档、CHANGELOG 与提交信息 |

**为什么区别对待**：客户端地址迟早要公开，藏它没有意义；而管理后台是刻意保持不公开的面，把它写进仓库——尤其本仓库是**公开仓库**——等于亲手取消这个设计。不链接挡不住专门找的人，但也没有理由主动把地址递出去。

**`zhitian-deploy` 更严格**：受版本控制的文件中**两个主机名都不得出现**，一律用 `CHANGE_ME_*` 占位符，真实值只进被 Git 忽略的 `.env`。这是「部署仓库必须自包含」原则的延续，与 `SERVER_PUBLIC_IP` 同一处理方式。

> 该规则确立于 2026-08-16。执行 agent 更新文档时若需要指代管理后台地址，写「企业管理后台主机名」或引用变量名，不要写出实际值。

### 云服务器现场操作：不归你

**你不具备云服务器访问能力。** SSH 登录生产服务器之后的一切动作——只读核对、`git pull`、`docker compose build/up`、重启、备份恢复、线上验证——由指挥师本人执行，**不会出现在给你的指令里**。若某条指令要求你连接服务器，那是指令写错了，应停下并向指挥师指出。

**仍归你的是 `zhitian-deploy` 中受版本控制的部署文件改动**：Compose、Nginx 模板、Dockerfile、部署文档。改这些文件时不要假设线上已生效——**「仓库已完成」与「生产已生效」是两件事**，你只能声称前者。

### 本机运行 compose 的约束

服务器不归你，但**本机跑 compose 归你**——改 `zhitian-deploy` 的 Compose、Nginx 模板或 Dockerfile 时你会在本地验证。以下两条与在哪台机器上跑无关，只与「跑 compose」这个动作有关：

1. **禁止输出完整 `docker compose config`。** 含真实 `env_file` 时它会展开全部密钥，2026-08-13 已真实误展开一次并触发密钥轮换。语法验证只用 `--quiet`；**也不要用 `--format json` 再管道过滤**——密钥已经进了进程输出，过滤只是没显示出来。
2. **`docker compose up -d` 不重建已有标签镜像**，也不因挂载内容变化而重建容器。代码、依赖、Dockerfile 或模型资产变化后必须显式 `build`，必要时加 `--force-recreate`；**「容器 healthy」不能单独作为版本正确的证据**——要查渲染后的实际配置。

## 四、编码规范

> 本章是项目通用编码规范的唯一权威来源；`zhitian_structure.md`只保留架构特有约束并链接到这里。

1. **Pydantic 模型**：层间数据必须用 Pydantic 模型，禁止裸 dict 传递
2. **业务逻辑在层内**：不写进 LangGraph 节点函数
3. **API Key 从 config.py 读**：禁止硬编码，新增 Key 在 .env + config.py 双写
4. **工具注册**：新增工具在 execution.py 的 `TOOL_REGISTRY` 中注册
5. **错误分级**：Level1（工具重试1次）→ Level2（规划降级llm_chat）→ Level3（返回统一错误）
6. **不静默吞异常**：异常必须记日志 + 按级别处理
7. **不硬编码语义**：能交给 LLM 的不写 if/else（如不写 `if "出门" in message`）
8. **日志脱敏**：用户消息只记 `message_len`，query/source 只记长度，异常只记 `error_type`
9. **.env 无 BOM**：UTF-8 编码，不能有 BOM 头
10. **文件头**：`# -*- coding: utf-8 -*-` + 中文注释说明文件用途

## 五、已知技术约束与踩坑

以下约束都是本项目真实踩过的坑，动相关代码前先看一遍：

| 约束 | 影响 | 注意事项 |
|------|------|---------|
| mcp 1.28.1 联动版本 | 已于 2026-07-15 升级，并联动精确锁定 `uvicorn==0.51.0`、`PyJWT==2.13.0` | 不要单独漂移其中一个版本；升级前需复核 FastAPI 启动、JWT 和 SSE 事件顺序 |
| Chroma 0.5.0并发与生命周期 | 初始化、读取、写入和删除已统一复用全局`RLock`；客户端仍是模块级单例，`close_resources()`无法主动关闭底层句柄（F39） | 新增任何Chroma入口必须复用`layers/chroma_sync.py`的同一把锁，不得另建互不协调的锁或改成每请求创建客户端；进程内换库需求出现时重新评估F39 |
| .env BOM 污染 | python-dotenv 无法识别首行变量名 | .env 改动后确认无 BOM |
| Docker Compose `env_file`插值 | 默认解析会把值中的`$...`当作变量引用，bcrypt哈希或未来外部凭据可能被误解析/截断；`format: raw`从Compose 2.30.0起可用 | 生产API的`env_file`必须使用`path + format: raw`长语法；部署前确认`docker compose version --short >= 2.30.0`，后端`.env`逐行采用不带引号的`KEY=value`。不得输出完整`docker compose config`，只用`--quiet`验证语法 |
| JWT_SECRET_KEY | 不能用占位值 | 必须在 .env 配置随机强密钥 |
| Codex 沙盒 PATH | 与本机不一致 | 运行时验证需用提权方式调 .venv\Scripts\python.exe |
| Python 3.10 | 不支持 `X \| Y` 类型语法在运行时求值 | 用 `Optional` 或 `Union`，或加 `from __future__ import annotations` |
| LibreOffice 转换 | `.doc/.xls/.xlsx/.ppt/.pptx` 转换依赖本机 `soffice`，并采用进程级串行锁和默认 30 秒超时 | 复用 `layers/converter.py` 和 `LIBREOFFICE_PATH`，不得绕过锁、超时及临时文件清理 |
| 聊天附件双生命周期 | 提取文本只在单进程内存中按 session 保存并默认 30 分钟过期；原始文件独立持久化到用户文件库 | 不要把文本 TTL 当成原始文件保留期，也不要把附件正文写入 SQLite、Chroma 或日志 |
| MCP 外部子进程 | `mcp_connector.py` 当前仅支持 stdio；直接继承完整环境会污染子进程，Windows 仅终止直接子进程会留下进程树 | 使用安全环境白名单并默认排除 `PYTHONPATH`；超时或取消必须终止整棵进程树并真实检查无残留 |
| 验证环境"富裕"掩盖缺陷 | F32（本机能装出NumPy 2.x但元数据层面合法，容器构建才暴露）与F37（本机有嵌入模型文件，CI因`.gitignore`排除该文件才暴露10 failed）为同一类问题：验证机器比目标环境（CI/容器）多出某个文件或依赖，导致改动在验证时"通过"，到目标环境才失败 | 任何改动依赖本机额外文件、环境变量或已安装依赖时，必须在等价于目标环境的条件下复测（如临时移走该文件模拟CI/容器环境），不能只在开发机验证通过就判定完成 |
| 内部验证脚本的外部调用副作用 | `search_documents`默认`enable_rerank=True`，会静默触发真实LLM调用；任何"验证内部逻辑/数据完整性"性质的脚本，如果调用链路上经过默认开启的重排/嵌入等外部依赖环节，会在未明确意图的情况下产生真实付费调用 | 编写此类脚本前，先确认调用链路是否会触达外部服务；如果本次验证目的不是测试该层，应显式关闭（如`enable_rerank=False`）或mock掉，而不是依赖"记得要说明"这种容易被忽略的自觉 |

## 七、更新 claude_memory.md 的规则

每轮工作结束时，`claude_memory.md` **必须**同步到当前状态（派给你的指令通常会在收尾步骤要求你更新，指挥师负责审阅）：

1. **当前进行中表格必须同步**：`上一轮完成` 更新为本轮实际改动的一句话摘要，`当前等待` 和 `下一步` 按讨论结果更新；这张表是下一个指挥师接手时第一眼看的地方，不能停留在上上轮的状态
2. **遗留问题**：新发现的问题加入表格，已解决的从表格删除（历史在 CHANGELOG）
3. **接下来规划**：根据本次讨论结果更新优先级和具体内容
4. **大问题总结**：如果架构级问题有变化（改善或恶化），更新描述
5. **已知技术约束**：新踩的坑加入表格

**原则**：只描述当前状态，不记历史。已修复的问题不留在文档里（CHANGELOG 里有记录）。

## 八、`CHANGELOG.md` 条目格式规范

- 新条目使用“标题行（日期+一句话概括）+ 最多3-5条bullet”的结构。
- 不按时间顺序复述探索过程，只记录改动文件或新增能力、关键真实验证数字（测试通过数、真实耗时、错误码）和最终结论。
- 推翻既有方案时必须说明“为什么变了”，但不展开中间debug过程。
- 中间失败和重试步骤通常不写入；环境变量污染、进程树清理等可复用通用教训例外，必须保留。
- 具体数字、bug结论、架构决定及理由、安全或权限行为变化不得为追求简洁而删除。
- **存档条目**写明提交、标签和远程；**普通工作条目默认不暗示已提交**，也不写版本号（打标频率见 8.1）。

### 8.1 版本号与标签语义

知天使用两段式功能版本 + 三段式文档补丁号，含义与知了hub 手册 8.1 一致：

1. **有实质代码改动或功能变化：** 使用 `vX.Y` 两段式标签，例如 `v3.3`、`v3.4`；阶段编号和跳号方式沿用项目既有习惯，不为套用通用语义化版本格式而强制改成三段式。
2. **只有文档或协作流程整理：** 使用 `vX.Y.Z` 三段式补丁标签，例如 `v3.4.1`。第三段表示紧跟最近一个两段式功能版本的非功能性整理；同一功能基线下如果连续发生多次此类存档，第三段依次递增。
3. **混合改动按代码变化处理：** 只要同一存档中包含实质代码逻辑、接口、数据结构、部署行为或用户可见功能变化，就不能使用文档补丁号掩盖，应按两段式功能版本处理。
4. **版本号必须能直接传达性质：** 看到两段式即可判断该存档可能包含功能/代码变化；看到三段式补丁号即可判断它只整理文档或协作流程，无需先翻提交正文才能分辨。
5. **四个仓库各自独立打标签**，版本号不强行对齐。后端与 `zhitian-deploy` 曾同时到 `v3.4` 属巧合，不构成约定。

> **本节 2026-08-18 补入。** 此前该语义只写在知了hub 手册 8.1，而知天**实际一直在用**（`v3.4.1` 到 `v3.4.5` 共 5 个，都是文档补丁号）——规则只落单边、靠人记得。第 2、3、4 条与知了hub 8.1 **逐字相同**。

#### 什么时候才打标签

**打标不必逐轮进行。** 提交与推送是安全网、每轮照常；标签是「值得回到这里」的锚点，**攒够了再打**：

| 情形 | 是否打标 |
|---|---|
| 真实行为变化，且准备部署 | ✅ 打两段式 `vX.Y` |
| 纯文档 / 流程整理 | ⏸ **累积若干轮后合并打一个**三段式 `vX.Y.Z`，不逐轮打 |
| 一个工作主题收尾 | ✅ 打，注释里列出覆盖了此前哪几条工作条目 |
| 服务器部署前 | ✅ 打，部署需要一个可回滚的锚点 |

- **不打标的轮次**：CHANGELOG 写**普通工作条目**——日期 + 概括，**不写版本号**、不暗示已存档；提交与推送照常进行。
- **打标的那一轮**：写**存档条目**，注明提交、标签、远程，并说明该标签**覆盖了此前哪几条工作条目**。

> **该约定 2026-08-18 由用户提出。** 起因是**四天内（08-15～08-18）打出了 9 个三段式补丁标签**（知了hub 4 个、知天 5 个），**全是文档整理，没有一个标记出真正不同的状态**。**标签一经推送不删不重打**，噪声会永久留在标签列表里。数字经 `git for-each-ref` 核实——初稿我凭印象写的「两天内六个」，天数和个数都不对。
> 需要注意的是：区分「存档条目 / 普通工作条目」这件事**知了hub 八章本来就写着**，只是此前每轮都被当成存档条目处理——**规则在手册里，执行时没照做**。

## 九、存档操作规范

Git 提交、推送和标签属于严格执行任务，默认由你完成（依据见一.5「存档职责划分」），并遵循：

1. 分别在**每个目标仓库**运行 `git status`、检查差异和忽略规则，确认没有运行时数据、构建产物、真实凭据或跨仓库误改。
2. 在写入 Git 历史前向用户列出**完整文件清单**；提交、推送和打标签**分别**以用户授权为准，授权提交不自动包含打标签或部署。
3. 使用**明确文件路径**暂存，不用模糊的全仓清理或破坏性 Git 命令；提交标题说明结果，正文说明主要能力、验证事实和仍未验证边界。
4. 推送目标分支后，以**本次完整提交哈希**确认远程同步；不能拿旧运行记录代替本轮验证。
5. 只有用户明确指定版本与标签信息时才创建带注释标签，并确认标签指向预期提交后**单独推送**。
6. 最终报告提交哈希、远程分支、标签（如有）、工作区状态，以及是否仍需生产更新。**多个仓库必须分别报告。**

## 十、部署验证四层

部署验证分四层，**报告必须写清完成到哪一层**：

1. **静态审阅：** 核对 YAML/Nginx 语法、占位变量、挂载、权限、路由和凭据排除。
2. **配置解析：** 使用现场或无敏感占位 `.env` 运行 `docker compose config --quiet`（**绝不省 `--quiet`**，理由见一.5「本机运行 compose 的约束」）；Nginx 使用 `nginx -t` 或官方容器检查。
3. **本地容器：** Dockerfile、依赖、挂载、启动命令、模型资产或运行时路径变化时，实际 `docker compose build`（必要时 `--no-cache`）和 `docker compose up`，验证 health、持久化与重启。`docker compose up` 不会保证自动重建最新镜像。
4. **真实部署：** 只有实际服务器上的 DNS、TLS、HTTP→HTTPS 跳转、两个子域名各自的入口、API 同源转发、Chroma 与 SQLite 持久化、备份恢复检查全部通过，才能写"线上通过"。**这一层不归你**（见一.5「云服务器现场操作」），由指挥师执行并回报证据。

如果任务明确限定为"只准备配置、不执行部署"，或环境确实缺少 Docker/Nginx，可以只完成前两层中的可用部分，但**必须列出未执行项**。涉及 Dockerfile、依赖或容器运行语义的改动，原则上应完成本地实际构建；做不到时**不能把静态审阅表述为可部署验证**。

> **本节 2026-08-18 补入**，对应知了hub 手册 7.4。此前知天只有红线里一句「本机验证结果不得冒充生产结果」，缺分层、也缺「报告须写清完成到哪一层」这个硬要求。第 1–3 层与知了hub 7.4 基本逐字相同；第 4 层按知天的部署面（双子域名、Chroma）调整，并补了「这一层不归你」——知了hub 那边同样由指挥师执行。
