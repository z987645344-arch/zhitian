# 知天历史架构决策

> 本目录保存已经讨论、验证或暂缓的架构决策历史，不代表当前执行计划。

## 2026-07-26 GraphRAG / PixelRAG方向评估

### 当时的产品阶段判断

项目当时仍以账号治理、组织权限和基础检索质量为主，GraphRAG与PixelRAG被判断为产品成熟后期的能力分支，不应抢占基础功能的开发资源。

### GraphRAG（知识图谱检索）

- **定位**：从“平面检索”（NaiveRAG，chunk独立打分）升级为“立体检索”（chunk之间建立实体关系网络），解决需要跨文档关联才能回答的问题。当时的BM25+向量+DeepSeek重排序属于加强版NaiveRAG。
- **成本结构**：建图阶段在文档入库时增加一次DeepSeek实体关系抽取；查询阶段图遍历使用本地算力，最终仍复用统一重排序，因此新增成本主要随文档上传频率增长，而不是随查询次数增长。
- **推荐形态**：采用“向量+BM25召回种子→图关系扩展→合并候选池→统一重排序”的串联融合，不额外依赖一个容易误判的简单/复杂问题分类器。
- **工程难点**：语义判断可以复用现有模型路由方式；实体关系抽取准确率、增量更新和图谱维护复杂度更高。

当时约定的重新评估信号：

| 编号 | 信号 |
|------|------|
| ① | 真实使用中反复出现必须跨文档关联、而现有检索答不出或答不全的问题 |
| ② | 文档规模显著增长，远超当时的几百chunk量级 |
| ③ | 使用者持续反馈检索结果零散、缺乏逻辑关联 |

### 2026-07-27实施与A/B结论

用户基于技术探索意愿决定提前实现，而不是因为上述信号已经出现。最终按串联融合模式落地，图数据保存在SQLite，功能默认关闭。

8份文档的现场A/B中，开关前后的最终候选完全相同，`adoption_rate=0.0`。当时全库仅8个chunk，而向量召回宽度已经覆盖全库，所有chunk都成为种子，没有图扩展空间。该结果验证了“语料规模足够大”是观察GraphRAG收益的必要前提。完整测试数字与实现过程保存在`CHANGELOG.md`的2026-07-27条目。

### PixelRAG（截图与视觉模型检索）

- **定位**：将网页或PDF渲染为截图tile，通过视觉模型理解表格、图表和版式，解决文字提取的信息完整度问题；它与GraphRAG解决的关联深度问题不同。
- **当时决策**：不实施。项目已经移除视觉模型配置，引入新视觉能力会重复MinerU时期“接入但长期无法形成稳定交付”的风险。
- **重新评估条件**：只有当真实文档中的图表/复杂表格显著增加，且现有文本提取持续漏失关键数据时，再重新评估。
