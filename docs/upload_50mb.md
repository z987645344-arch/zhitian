# 50MiB上传边界与隔离测量

所有文件入口默认每文件50MiB。知识库资料依然长期保存；聊天原件和产物遵循`chat_temporary_files.md`的临时生命周期。体积达标不是一定可处理：PDF200页、每图/栅格页面20MP、聊天正文50,000字、入库2000切片保持原值，扫描PDF不支持OCR。超过边界明确拒绝，不返回部分结果。

## 分层限额

- API multipart解析前限制单次请求总量为50MiB+512KiB封装余量；逐文件再严格校验50MiB。多文件/多原件合计超限需分批，不表示每份都能同时50MiB。
- 超过10MiB的上传及同步处理最多一个；达到上限立即429，完成/失败/取消释放。知识库原件清理后，后台向量化继续由现有入库槽位与内存账本约束。
- 转换服务输入和输出各50MiB，串行、无排队原件；繁忙明确拒绝。API2GiB、tmpfs512MiB；转换1GiB、tmpfs256MiB。tmpfs计入内存，不能把swap算余量。
- 部署反代52m留封装空间；外层zhiliao-gateway另行同步，不在本轮修改。生产.env若显式写5MiB，要同步50，否则新默认不生效。网页动态读取上限，失败回退50MiB。

## 实测口径

仅现场编造的约48–49MiB样本：DOCX/PPTX/XLSX含16张独立随机PNG，文字PDF8700页、扫描PDF16页。断网内部Docker网络，API2GiB、转换768MiB，非root、只读根、一次性tmpfs，无真实.env、业务卷或模型联网调用；本地ONNX只做一次嵌入预热。真实HTTP流式multipart，20ms采样cgroup memory.current及减inactive_file后的工作集和tmpfs占用。不是TestClient拼接整个50MiB请求的内存读数。

51MiB真实HTTP请求在解析前返回413和“单次上传总量不能超过50MB，请分批或拆分后上传”。大文件上传、任务完成、审核、回执清理均未调用付费模型。

此compose服务物理上限合计3.375GiB；8GiB宿主余下约4.625GiB须供系统、网关和其他服务。这是配额总账，不是宿主实测空闲量。高压缩率Office、更多嵌入对象及不同PDF密度仍可能触发既有执行时间/内存/质量限制；50MiB不承诺任何内容都能完成。

页数建议暂保留200：本次文字PDF是8700页压力夹具，证明拒绝清楚，而非足以证明放宽安全。像素20MP及正文/切片上限同样不动。App的`lib/services/api_service.dart`仍有5MiB前置常量，影响`chat_provider.dart`附件和`toolbox_page.dart`工具上传；后续需更新此前置限制和临时文件生命周期，本轮不改App，只保证后端明确错误。

实验样本、容器和一次性目录用完删除，只保留忽略目录中的匿名资源读数；默认data大小、修改时间、SHA-256前后核对。
