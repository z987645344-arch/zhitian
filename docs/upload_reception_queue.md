# 员工上传接收排队

只有员工、审核员的知识库上传和文字录入使用本队列，客户入口不排队。默认共享6位、员工紧急1位、每位320MiB预留均不变。

## 流程

1. 有空位：沿用同步解析、切片、查重和原有入库队列的流程。
2. 满位：完成原有便宜检查（权限、账号在途数、格式、大小、加密、组织内已入库内容查重），限额核对后落到运行器身份工作区，创建pending任务，立即返回accepted和任务号。
3. FIFO队头获取共享/紧急处理位后，使用同一套解析函数。等待不挂着HTTP，也不消耗转换/解析的原时限；拿到位后仍用原时限。
4. 删除原件、释放处理位和大文件闸门后，使用原入库队列。任务号、权限校验和进度接口全程不变。

处理位分配和排队检查共用临界区。只要仍有待拿位的员工，后来的客户不能取得已释放的共享位；客户也永远不能用紧急位。FIFO保证拿位顺序，不强行串行化已经拿位后的解析/入库完成顺序。

## 默认限制

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| UPLOAD_RECEPTION_QUEUE_LIMIT | 6 | 还未获得处理位的接收任务数 |
| UPLOAD_RECEPTION_QUEUE_WAIT_SECONDS | 300 | 接收队列等待上限（秒） |
| UPLOAD_RECEPTION_QUEUE_MAX_BYTES | 134217728 | 原件总字节上限，128MiB |

原件字节额直到原件实际清理才释放，包含已经拿位但尚未解析完成的任务，不重复申请320MiB处理位预留。默认512MiB tmpfs不能全用于排队：128MiB为排队原件上限，其余留给multipart落盘副本、转换及解析中间文件。该配额不是磁盘空间保证，实际空间不足仍明确拒绝并回收。

最大50MiB的原件可容纳2份，第3份会超过128MiB；较小文件仍最多6份。大文件可以逐份接收入队；沿用原“超过10MiB同时最多1份”的闸门，后台处理也使用该闸门，忙时新大文件可能在接收前就得到原来的可读拒绝。员工每账号2份在途上限包含排队任务。

## 错误和恢复

- 429 / upload_queue_full：上传排队已满，请稍后再试。
- 429 / upload_queue_bytes_full：上传排队的文件总量已达上限，请稍后再试。
- failed / upload_queue_timeout：排队超时，请稍后重试；原件清理。
- 503：上传暂存空间不足或不可用，请稍后重试。
- 原物理内存准入拒绝仍为429 / heavy_task_busy，不排队掩盖内存不足。
- 已受理后的解析错误用任务error_message返回，与同步路径一致；SSE/查询均做本人归属校验。

队列、处理位和账号计数仅在单进程API内协调。正常退出取消排队/新后台任务，等待可终止运行器清理后释放资源；中途崩溃后，启动恢复把未完成任务标为interrupted，并按既有服务标记、PID身份规则清理失效目录。原件不入备份，不保证重启后继续排队。

## 部署

先部署API，再部署管理端。生产.env不必新增配置；保持现有上传tmpfs 512MiB和TMPDIR设置，不改变容器内存限额或入库队列配置。不支持多个API worker或副本共同使用这份进程内队列。更新/回滚前可等待在途任务完成，否则须接受中断后重新提交。
