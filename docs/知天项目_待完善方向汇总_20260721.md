# 知天项目 · 待完善方向汇总

> 整理自 2026-07-21 面试环节讨论,按主题分类,标注对应根源问题与优化方向。
> 说明:P0/P1/P2 为本文对紧迫度的粗略分级,不是正式排期,具体顺序建议后续和指挥师讨论后再定。

---

## P0 · 安全与权限类

### 1. 账号管理能力缺失(第三方审计已确认)
- **现状**:无 list/delete/disable/change_role/reset_password 任何管理接口;注册端点无限流,可被批量注册;无密码找回,忘记密码即永久锁死。
- **已有方案**:完整的多角色注册审批体系设计文档已就绪(customer/employee/reviewer/开发者四类身份、企业密码机制、默认账号自毁机制),尚未转化为 Codex 指令落地。
- **可立即执行的子步骤**:把"开发者视图"标签及系统提示词模块编辑权限从 reviewer 侧边栏收回——不依赖完整体系落地,能直接堵上下面第2项的越权口子。

### 2. reviewer 对开发者视图/系统提示词模块存在越权访问
- 审核员目前可以看到并编辑系统提示词模块(规范/语气/禁用),这不在其职责范围内。
- 属于第1项的一个具体子问题,建议优先单独处理。

### 3. 外网知识库(Tavily)接入无注入防护
- 目前只有"结果质量"层面的四条降级规则(异常/空结果/低分/整理失败),**没有任何应对间接 prompt injection 的机制**。
- 缺失的具体防护层:
  - 检索内容与指令在 prompt 结构上没有做边界隔离标记
  - 没有对外部内容做注入特征扫描/过滤
  - 没有把"由外部内容触发的行为"做执行权限收紧(比如禁止外部内容触发写操作/文件生成类工具)
  - 没有生成结果的输出侧异常校验
  - 没有来源可信度分级机制
- 建议优先级最高的单项:执行权限隔离——不依赖"能否100%检测出注入"这个很难保证的前提,直接从权限设计上锁死最坏情况的破坏半径。

## P1 · 生产可靠性类

### 4. 数据库 schema 变更缺少强制迁移流程
- 目前是"改表结构可能需要迁移脚本"的非强制状态,不是每次变更都必须走可执行、可回滚的迁移脚本。

### 5. 无自动备份与备份可恢复性验证
- 升级前没有自动快照备份机制;即便日后补了备份,也需要配套"定期验证备份真的能恢复"的演练机制,而不是只确认文件存在。

### 6. 无升级前后数据完整性校验
- 缺少"升级前后对比关键表行数/校验和"这类机制,目前只能靠"应用能正常启动"这种弱信号判断升级是否安全。

### 7. 无灰度发布机制
- 私有化单实例部署模式下,"灰度"应理解为"分批次、企业自愿选择升级窗口",而非传统流量切分。
- 目前完全空白:无稳定版/预览版通道区分、无升级前通知确认环节、无双写过渡期设计、无明确的自动回滚触发标准、无升级后复盘记录习惯。

### 8. 前后端接口契约未版本化
- 接口没有 `/v1/`、`/v2/` 路径级版本管理,没有向后兼容保证,没有契约回归测试,客户端也没有连接时的版本兼容性检查。
- 目前是"后端改接口,前端跟着同步改"的强耦合演进模式,规模小时问题不显现,一旦有多个企业各自部署不同版本的客户端,风险会直接暴露。
- **设计原则(2026-07-21 讨论确认)**:参考游戏/App"客户端发包、服务端实时"的模式,但不能整体照搬——真正该按此模式拆分的是以下三层,不能混为一谈:

  | 层面 | 处理方式 |
  |---|---|
  | 后端数据与业务逻辑(知识库内容、检索、模型推理) | **保持实时、持续迭代,不冻结**——这是 RAG 产品"能查到最新知识库内容"这一核心价值所在,冻结成快照会让产品退化成静态问答系统 |
  | 客户端(Flutter Windows 应用) | **版本化封包 + 用户主动更新 + 稳定版/预览版通道**,类比游戏客户端补丁/App 安装包 |
  | 前后端接口契约(数据返回的字段结构/协议格式,不是数据内容本身) | **冻结 + 版本化 + 给出兼容期承诺**——后端内部逻辑可以持续迭代,但对外暴露的接口形状在承诺窗口期内不能破坏性变更,新版本走独立路径,旧路径过渡期后再下线 |

  一句话概括:**实时的是数据内容,冻结/发包的是数据的呈现结构和客户端本身**——这样后端能不受限迭代,前端能按自己节奏发包更新,老版本客户端依然能拿到实时最新数据,不会因为后端持续升级而解析失败。

### 9. 依赖未锁定版本(12个)
- bcrypt/slowapi/openai/pdfplumber 等依赖未锁死具体版本号,存在环境不一致风险。

### 10. 可观测性薄弱
- 目前监控只在进程内存里,重启即清零,没有外部告警通道(对应审计 F16)。

## P2 · 检索质量与规模化类

### 11. 文档检索缺少 query 改写能力
- query 改写目前只覆盖联网搜索链路(且改写失败会直接退回用原 query),企业文档 RAG 检索没有对应机制,只有分数阈值+标题/来源命中加权做兜底,不是真正的语义改写。

### 12. fast 模式无法主动反问澄清
- `clarify` 意图分支只存在于走 classify 节点的 expert 模式;fast 模式为省调用次数直接跳过 classify,无法识别"问题信息不足该反问"这种情况。

### 13. 文档更新缺少版本替换机制
- 同一文档重新上传修订版时,没有确认是否会先清理旧版本对应的旧 chunk 再插入新内容,存在新旧版本并存、检索结果新旧混杂的风险。

### 14. 重排序完全依赖远程 API,无本地降本方案
- `_rerank_candidates` 目前 100% 依赖 DeepSeek 远程调用做打分,没有本地轻量 cross-encoder 或 LTR 模型作为替代/补充,调用次数和延迟都跟随语料库规模线性增长。

### 15. 检索相关的关键常量全部硬编码,无动态配置能力
- `top_k`、召回倍数、`RERANK_CANDIDATE_COUNT`、`RAG_SCORE_THRESHOLD` 均为写死的常量,不随语料库规模自适应,也没有配套的候选拥挤度/重建耗时监控信号。

### 16. BM25 索引懒重建策略,规模变大后重建耗时无监控
- 审核/删除后标脏、下次检索时(可能是全量)重建,语料库变大后重建耗时可能出现明显毛刺甚至超时,目前没有对重建耗时做任何监控或告警。

### 17. 语料库规模增长导致的检索精度衰减,无系统性治理机制
- 缺少:按业务域/部门做元数据预过滤分区检索、近似重复文档的去重/合并机制、针对企业内容微调的 embedding 模型评估、持续的检索质量评测闭环(标准 query 集 + 定期回归)。

### 18. 无系统级沙盒
- 目前仅 MCP 外部子进程有"环境变量白名单 + 进程树清理"这一项进程级隔离,没有容器级隔离、文件系统访问限制、网络出口白名单等完整沙盒能力。现阶段无代码执行场景,暂不算紧迫,但 MCP 外部工具接入范围扩大后需要重新评估。

### 19. 联网检索(search_web)与 Tavily 强绑定,缺少供应商可替换的抽象层
- **现状**:`search_web` 在 `TOOL_REGISTRY` 里是固定工具位置,但内部实现直接调用 Tavily SDK,降级规则(异常/空结果/低分/整理失败四条)和字段处理都跟 Tavily 的具体返回结构绑在一起,换供应商需要动检索逻辑本身。
- **风险**:企业级产品不应对单一第三方检索服务高度依赖——涨价、限流、被更优检索质量的供应商替代时,切换成本过高。
- **设计方案(2026-07-21 讨论确认)**:在 `search_web` 和具体供应商之间加一层 `WebSearchProvider` 抽象接口(固定契约:输入 query,输出统一格式的候选列表——标题/摘要/来源/分数),现有 Tavily 实现改造成该接口的一个具体实现类;四条降级规则和后续要补的注入防护逻辑应挂在抽象层统一处理,不随供应商变化而重复实现。换供应商只需新增实现类+改配置项,不用动 `classify`/`plan`/`reflect` 等上层业务逻辑,也为未来"多供应商并存、按场景路由"留了扩展空间。
- **不建议的方案**:把 Tavily 迁移到真正跨进程的外部 MCP 协议(`mcp_connector.py` 那条路径)——这是更重的方案,只有在需要真正进程隔离或要把该能力开放给外部第三方 MCP 客户端调用时才值得,单纯为了"可替换性"和"代码整洁"不划算,而且会让本就还没补的注入防护逻辑更难实现(需要跨进程边界处理)。现有 `TOOL_REGISTRY` + `mcp_client` 的进程内注册表模式已经提供了足够的调用入口整洁度。

## 备注
- 第 1、3 项是本次讨论中明确定级最高的两项,且都有"可以立即启动、不依赖完整体系"的子步骤,建议作为下一轮 Codex 指令的优先候选。
- 第 4-8 项(生产可靠性)建议在"正式提供给第一个非自用企业客户"之前必须补齐,不属于可以无限后置的锦上添花项。
- 第 11-19 项(检索质量与规模化)目前语料库规模小,问题尚未真实显现,但均属于"规模上来后才会突然暴露"的架构债,建议提前规划、分批处理,不需要现在一次性全做。第 19 项(联网检索供应商抽象)投入成本相对低,可以优先于其他几项单独排期。
